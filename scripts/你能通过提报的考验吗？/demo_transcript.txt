与仓库 solver 的对应关系
------------------------
  n 的恢复   = scripts/你能通过提报的考验吗？/solve_tibao_lsb.py
               （divine(2)/divine(4)/divine(8) -> 两个差 -> gcd -> 试除小素数）
  明文还原   = scripts/solve_tibao.py
               （逐位收集 B，再用 ceil(n*B/2^k) 还原）

  因为本地服务每次启动都会随机生成 n 和 coreflame，而仓库 solver 把
  IP/端口/核心密文写死在文件里，所以演示脚本只替换了这三个常量
  （coreflame 改为从 banner 读取），攻击逻辑一行未改。

  注：solve_tibao_lsb.py 里那版 "low/high + mid 二分" 在整数取整下会漂移
  （2048 位时偏差可达数百），因此本演示采用 solve_tibao.py 的 B/ceil 写法，
  它才是精确的。两版都在仓库里，属于同一个作者的两条实现路线。

e 的作用边界
------------
  * e 只被服务端用来加密：c = m^e mod n。
  * 客户端全程不需要 e：divine(2) 的返回值本身就是 2^e mod n，直接当
    "乘 2 的算子"用。所以题面"九位往上，十六位封顶"只是干扰/校验线索。
  * 服务端把 e 限制在 9~16 位：random.randrange(256, 65536) | 1，并断言
    9 <= e.bit_length() <= 16，同时要求 gcd(e, φ(n)) = 1。
  * 启动日志里会打印 e 的十进制值与位数，见下方 "e 是否落在题面 9~16 位范围: YES"。

读这份输出的四个要点
================================================================

1) 前 10 位为什么全是 0 —— 不是 bug
   n 是 2047 位，而明文 m = b'YulinSec{local_lsb_oracle_demo}' 只有 247 位
   （B 的位数 = 247）。也就是说 m/n ≈ 2^-1800，m 落在 [0, n) 的最左端，
   所以 m/n 的二进制展开前 1800 位必然全是 0。
   这正好对应输出里"区间宽 ≈ 2^2046 一路减半到 2^1534 / 2^1022 / 2^510"：
   很长一段都在往左半区收，直到逼近 m 的真实位置才开始出现 1。
   真实题目的 flag 也只有 30 字节左右，现象完全一样。

2) gcd 收敛时多出的倍数 4 —— 这就是 strip_small_factors 的存在理由
   本次运行：
       gcd(c2²-c4, c2³-c8) 的位数 = 2049（比 n 多 2 位）
       校验 d1 % n = 0, d2 % n = 0
       gcd 比 n 多出的倍数 = 4
   因为两个差都是偶数（各带因子 4），gcd 把 4 一起捞了上来；
   真 n = p·q 不含小因子，按 2,3,5,... 试除一遍就回到 2047 位的 n。
   如果换成 solve_tibao_lsb.py 里那句"直接拿 gcd 当 n"，后面 pow 全错。

3) floor 与 ceil 只差 1，但明文最后一个字节就废了
   正常（ceil）： b'YulinSec{local_lsb_oracle_demo}'   -> 验证 True
   floor 版   ： b'YulinSec{local_lsb_oracle_demo|'    -> 验证 False
   注意最后那个字符：'}' 是 0x7d，'|' 是 0x7c，正好少 1。
   floor 相当于把"区间左端点向上取整"改成了"向下取整"。

4) 分支反了 —— 得到的是一个完整但错误的大整数
   reversed 版输出的 m 有 500 多位十进制，bytes 是满屏乱码，
   divine(m) != coreflame。原因是把 bit=1 当成了"下半区"，
   区间每一步都朝远离真实 m 的方向收缩。
   唯一能发现它的办法：最后用剩下的一次 divine 做验证
   （服务端限 8 次，恢复 n 用 3 次、验证用 1 次，共 4 次，余量充足）。
